How the mnemonic and backup shares encode the same secret

The thing being backed up is entropy, not the everyday spend key. The twelve-word phrase and the current 2-of-3 paper shares are two encodings of those 16 bytes. primaryKey at m/0'/0' is derived from them and cannot be inverted.

The one-sentence model

Entropy is the master secret. The mnemonic is BIP-39 of that entropy. Current backup shares are Shamir of a tagged 32-byte wrapping of that entropy. primaryKey is a hardened child of the seed built from the mnemonic, so it is a consequence — never a backup of the phrase.

The four objects

Names in this page are the names in the app (utils/mnemonicWallet.ts, utils/backupShares.ts). BRC-157 calls m/0'/0' the “root key”; here that child is primaryKey, and rootKey is the BIP-32 master above it.

entropy

16 bytes / 128 bits. The only secret that both backup media reconstruct.

  • Produced by Mnemonic.fromRandom()
  • Read back with toEntropy()
  • v2 paper only supports this width

mnemonic

12 English BIP-39 words. A lossless, checksummed spelling of entropy.

  • fromEntropy / toEntropy are inverses
  • Checksum is 4 bits of SHA-256(entropy)
  • This is what vault recovery also needs

backup shares

Three BRC-140 strings, any two recover. They do not split primaryKey.

  • Split subject: framed entropy, 32 bytes
  • Format: x.y.threshold.integrity
  • Default: 2-of-3, non-deterministic points

primaryKey

The wallet’s everyday private key, at hardened path m/0'/0'.

  • Identity key is its compressed public key
  • Fed to SimpleWalletManager
  • Cannot rebuild entropy or the phrase

Mnemonic and entropy are the same 128 bits

A new wallet calls Mnemonic.fromRandom(), which draws 128 bits. BIP-39 appends a 4-bit checksum (the first bits of SHA-256(entropy)), splits the 132 bits into twelve 11-bit word indexes, and looks them up in the English wordlist. 

entropy          = 16 bytes
checksum         = first 4 bits of SHA-256(entropy)
mnemonic         = 12 words  (132 bits = 128 + 4)
Mnemonic.toEntropy()     → those 16 bytes
Mnemonic.fromEntropy(e)  → the same 12 words
Do not use fromEntropy as a classifier

Mnemonic.fromEntropy computes the checksum. It accepts any 16 bytes and emits a valid-looking phrase. That is why recovery does not “rebuild a mnemonic and see if the checksum works” to decide whether paper is v2 or legacy — the check can never fail. Classification is the SHA-256 tag on the 32-byte payload, below.

From the phrase, the everyday key is derived exactly as BRC-157 specifies for the spend root. The app already did this before the paper format changed; only the share payload changed. 

seed       = mnemonic.toSeed('')                          // PBKDF2-HMAC-SHA512, 2048 rounds
hd         = HD.fromSeed(seed)
rootKey    = hd.privKey                                   // BIP-32 master
primaryKey = hd.derive("m/0'/0'").privKey.toArray()       // hardened
identityKey = that key’s compressed public key

Current paper: tagged entropy, then Shamir

BRC-157 says: split the entropy, not an operational key. The app does that, with one extra wrap that the printed page never has to mention.

toBackupShares always splits a 32-byte secp256k1 scalar. Raw 16-byte entropy is the wrong width. Left-padding it to 32 bytes (the BRC-157 import recipe) would look like sixteen leading zero bytes — distinguishable from a random primaryKey until someone imports a 24-word phrase, whose entropy is already 32 bytes and byte-identical in length to a legacy key. Length cannot decide.

So the current format, in frameEntropy, is always exactly:

bytes 0–15 · entropy
the 16-byte secret from toEntropy()
bytes 16–31 · tag
SHA-256(entropy)[0..16]
payload = entropy(16)  ||  sha256(entropy).slice(0, 16)     // always 32 bytes
shares  = new PrivateKey(payload).toBackupShares(2, 3)

That PrivateKey is a carrier. It is not primaryKey, it is not used to sign, and it must not appear on-chain. It exists so BRC-140 can treat the tagged payload as a field element and split it.

Share string

Each printed / QR’d share is four dot-separated fields (BRC-140):

base58(x). base58(y). 2. a1b2c3d4
x · y — Shamir point over the secp256k1 field prime 2 — threshold (any two recover) integrity — first 8 hex chars of HASH160(compressed pubkey of the carrier)

All three shares share the same integrity tag. The scanner rejects a share whose tag disagrees — that is what stops someone mixing a v2 page with a leftover v1 page of the same wallet. The two formats split different 32-byte values, so their tags never match.

24-word imports are refused at print time. Their entropy is 32 bytes, which fills the carrier and leaves no room for the tag. Those wallets keep the phrase as their only paper path. The app has never generated anything but 12 words.

Recovery: recombine, pad, then classify

1

Scan any two shares. Parse x.y.threshold.integrity. Same threshold, same integrity, not a duplicate point.

2

Recombine with PrivateKey.fromBackupShares. Lagrange interpolation at x = 0 yields the 32-byte carrier as a BigNumber.

3

Pad. toArray() drops leading 0x00 bytes (~1 in 256 payloads). padPayload left-pads back to 32. Without this, both formats mis-decode.

4

Classify. If bytes 16–31 equal sha256(bytes 0–15)[0..16], this is v2 entropy. Otherwise it is a legacy primaryKey.

5

v2: Mnemonic.fromEntropy(entropy) → setMnemonic → buildWalletFromMnemonic. The wallet is identical to one that never left the phone. Any stale recoveredKey is deleted only after the mnemonic write succeeds.

6

Legacy: treat the 32 bytes as primaryKey, store WIF, buildWalletFromRecoveredKey, and tell the user these pages cannot open a vault. 

function classifyPayload(raw) {
  const payload = padPayload(raw)          // left-pad to 32
  const entropy = payload.slice(0, 16)
  const tag     = payload.slice(16)
  const expect  = sha256(entropy).slice(0, 16)
  return tag matches expect
    ? { kind: 'entropy', entropy }
    : { kind: 'legacy',  primaryKey: payload }
}

A corrupted tag is classified as legacy rather than as a wrong phrase. Collision chance for a random 32-byte key against the tag is 2−128.

Phrase and current paper are interchangeable. That is the whole point of moving the split subject from primaryKey to entropy.

Legacy paper still works, and stays legacy

Older sheets split the raw primaryKey bytes — the hardened child itself. Recovery still accepts them: the tag check fails, so classifyPayload returns { kind: 'legacy', primaryKey }.

A wallet that was itself restored from those sheets has no mnemonic in storage. It can only print more legacy shares, via generateLegacyKeyShares. There is no in-place upgrade: you cannot invert m/0'/0' back to entropy. The remedy, if the phrase is truly gone, is sweep to a fresh 12-word wallet and print v2 paper.

Why the printed page has no version field

Sheets already in drawers cannot grow a version marker. The 16-byte SHA-256 tag is the version, living inside the secret so old and new paper stay the same string shape and the same QR scanner.

Why the vault forced this change

The v2 vault key is not a second phrase. It is the same mnemonic pushed through BIP-39 with a non-empty passphrase: 

main wallet : HD.fromSeed(mnemonic.toSeed(''))
vault HD    : HD.fromSeed(mnemonic.toSeed(passphrase))   // empty passphrase refused

Deposit addresses are ordinary BIP-32 children of that vault node. Recovery is therefore either YubiKey+PIN, or mnemonic + passphrase. There is no third path. A backup that only returns primaryKey restores the hot wallet and bricks the vault.

Current paper is seed-equivalent

Any two v2 pages rebuild the twelve words. Treat two pages together the way you treat the phrase. A single page still reveals nothing (Shamir below threshold).

Worked example (BIP-39 test vector)

Public vector, not a real wallet. Same numbers as BRC-157’s 12-word example.

mnemonic  = legal winner thank year wave sausage worth useful legal winner thank yellow
entropy   = 7f7f7f7f7f7f7f7f7f7f7f7f7f7f7f7f          // 16 bytes
tag       = 87dcde7fa6df23e15fa7ba9b2a1f3140          // sha256(entropy)[0..16]
payload   = 7f7f7f7f7f7f7f7f7f7f7f7f7f7f7f7f
            87dcde7fa6df23e15fa7ba9b2a1f3140          // 32-byte carrier

// After any 2 shares are recombined and padded:
classifyPayload(payload) → { kind: 'entropy', entropy: 7f7f…7f }
Mnemonic.fromEntropy(entropy) → the same 12 words

// Everyday key, from the phrase, not from the carrier:
primaryKey @ m/0'/0'
          = 27e442c8015fc055789d6628f3b30461e8b2598aff74dc87ceef00dd8e670e55

Notice the carrier and primaryKey are different 32-byte strings. Feeding the carrier to buildWalletFromRecoveredKey would open a valid-looking empty wallet. Classification exists to make that mistake impossible without a 2−128 tag collision.

If this same phrase had been backed up the old way, the split subject would have been 27e442…0e55 itself. Any two of those pages still spend, and none of them can ever emit legal winner … yellow.
